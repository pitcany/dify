Retrieval weight tuning · v1 validation

Weight Tuning Field Trial

A four-week plan to find out whether thumbs-up/down feedback is enough to recommend better semantic/keyword weights for deployed chatflows, before anyone builds an "apply" button.

Branch feat/retrieval-weight-tuning Scope recommend-only, no weights change Length about 5 weeks

What we need to learn

The code is finished and tested on synthetic data. Four questions can only be answered with real traffic:

  • VolumeDoes any weighted search collect 30 liked and 30 disliked traced conversations within the 30-day window? If not, the report will only ever say "not enough feedback".
  • CostHow much storage does tracing take, and does it slow the knowledge-retrieval node down?
  • StabilityDoes the recommendation stay put week to week, and does it stay quiet when the feedback is pure noise?
  • CorrectnessWhen the report suggests a new weight, do people actually judge the resulting chunks as more relevant?

What the report gives us

For each weighted search in a node, the report replays the recorded candidates under every semantic weight from 0 to 1 and compares liked against disliked conversations. A suggestion looks like this:

Example
Current
semantic 0.700.30
Suggested
semantic 0.600.40
Semantic (vector)Keyword
Example output
$ flask retrieval-weight-report --tenant-id <workspace> --app-id <app>
Node 1718…, cross-dataset merge (openai/text-embedding-3-small), current vector weight 0.70
  Recommend vector weight 0.60 (keyword 0.40).
  Best weight 0.60: improvement +0.180 [+0.060, +0.290], stability 74%,
  changes results for 22% of rated runs (41 liked / 33 disliked).

A change is only suggested with at least 30 liked and 30 disliked runs, a move of 0.1 or more, a 90% interval above zero, and a best weight that 60% of resamples agree on.

Plan

  1. Week 0

    Pick pilot apps and turn tracing on

    Find chatflows that both use weighted-score retrieval and already get feedback. Aim for two or three apps with at least 100 rated conversations a month.

    Rated chatflow conversations in the last 30 days:

    SELECT a.id, a.name, f.rating, count(*) AS feedback
FROM message_feedbacks f
JOIN messages m ON m.id = f.message_id
JOIN apps a     ON a.id = m.app_id
WHERE a.mode = 'advanced-chat'
  AND m.workflow_run_id IS NOT NULL
  AND m.created_at >= now() - interval '30 days'
GROUP BY a.id, a.name, f.rating
ORDER BY feedback DESC;

    Which of them use weighted scores, at the node or in a dataset's hybrid search:

    -- Node-level weights (multi-dataset merge) in the published workflow
SELECT a.id, a.name
FROM apps a JOIN workflows w ON w.id = a.workflow_id
WHERE a.mode = 'advanced-chat' AND w.graph LIKE '%weighted_score%';

-- Datasets whose own hybrid search uses weights
SELECT id, name FROM datasets
WHERE retrieval_model->>'search_method' = 'hybrid_search'
  AND retrieval_model->>'reranking_mode' = 'weighted_score';

    Then set RETRIEVAL_WEIGHT_TRACE_ENABLED=true and keep RETRIEVAL_WEIGHT_TRACE_SAMPLE_RATE=1.0, so every rated conversation in the pilot apps counts. Run the migration first.

    The setting covers the whole deployment, so every published chatflow with weighted retrieval gets traced, not just the pilots. If storage matters more than coverage, lower the sample rate, or add a small per-app allowlist before starting.

  2. Week 1

    Check health and cost

    • Rows and size after the first full day. A traced conversation stores roughly 3–10 KB (one row per weighted search, 10–20 scored candidates each). Multiply by daily traced runs and 30 days of retention.
    • Knowledge-retrieval latency, p95 by day, compared with the week before tracing.
    • Logs for Failed to persist weighted-score traces and Failed to report weighted-score observation. Both should be absent or rare.
    • The daily cleanup task clean_retrieval_weight_traces_task runs on the beat schedule.
    SELECT count(*) AS rows,
       pg_size_pretty(pg_total_relation_size('retrieval_weight_traces')) AS size
FROM retrieval_weight_traces;

SELECT date_trunc('day', created_at) AS day,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY elapsed_time) AS p95_seconds
FROM workflow_node_executions
WHERE node_type = 'knowledge-retrieval' AND app_id = :app_id
  AND created_at >= now() - interval '14 days'
GROUP BY 1 ORDER BY 1;

    The latency query assumes node executions are stored in the database (the default WORKFLOW_NODE_EXECUTION_STORAGE=rdbms).

  3. Weeks 2–4

    Collect and snapshot weekly

    Once a week, save the JSON report for each pilot app. Keep the snapshots; the stability check in week 5 compares them.

    flask retrieval-weight-report --tenant-id <workspace> --app-id <app> --json \
  > reports/<app>-$(date +%F).json

    Track how fast evidence builds up, per app:

    SELECT t.app_id,
       count(DISTINCT t.workflow_run_id) AS traced_runs,
       count(DISTINCT f.message_id)      AS rated_runs
FROM retrieval_weight_traces t
LEFT JOIN messages m          ON m.workflow_run_id = t.workflow_run_id AND m.app_id = t.app_id
LEFT JOIN message_feedbacks f ON f.message_id = m.id
GROUP BY t.app_id;
  4. Week 5

    Analyze

    Four checks, in order. The first three need a small offline script built on the existing domain module; nothing extra runs in production.

    • Replay sanity. For a sample of real traces, replaying at the recorded weights must reproduce exactly what was shown. Any mismatch means the trace data is wrong, and everything after it is void.
    • Placebo. Shuffle the like/dislike labels 20 times and rerun. A suggestion should appear in at most 2 of the 20 runs. More than that means the thresholds let noise through.
    • Holdout. Pick the weight from weeks 1–2 only, then score it on weeks 3–4. The improvement must stay above zero on the later half.
    • Human judgment. For each unit with a suggestion, take 30 disliked and 30 liked queries. Show a reviewer the top results under the current and the suggested weight, in random order and unlabeled, and ask which set answers the question better.
  5. Week 6

    Decide

    Apply the rules below and record the result with the evidence: snapshots, placebo rate, holdout scores, and review tallies.

Decision rules

OutcomeWhenNext step
Go At least one unit reaches the evidence bar; placebo suggestions ≤ 2 of 20; holdout improvement > 0; reviewers prefer the suggested results on most disliked queries and do no worse on liked ones. Design Phase 2: a one-click "apply" for owners, with a per-app override and rollback.
Adjust Too little evidence in 30 days. Lengthen retention to 60 days, lower the per-rating minimum, or pool evidence across apps that share a dataset.
Adjust Enough evidence, but placebo or holdout fails, or reviewers see no difference. Feedback is too coarse. Try the opt-in mode where an LLM rates each candidate's relevance, using the app's model credits.
Stop Replay sanity fails, tracing costs more than it is worth, or no app combines weighted retrieval with real feedback. Turn tracing off and fix or shelve. Existing traces expire on their own.

Risk and rollback

  • Set RETRIEVAL_WEIGHT_TRACE_ENABLED=false to stop tracing immediately. Traces expire after the retention window, and deleting an app removes its traces.
  • Traces store chunk ids and scores, never the query text or chunk content.
  • Retrieval results never change. A failed trace write is logged and dropped, and the node still succeeds.
  • The migration only adds the retrieval_weight_traces table. Test it on a staging copy first; so far it has only been checked against SQLite in unit tests.

Decisions needed before week 0

  • Which deployment and which pilot apps.
  • Whether whole-deployment tracing is acceptable, or a per-app allowlist should be added first.
  • Who saves the weekly snapshots, and who reviews results in week 5 (people who know the knowledge bases are best).
  • Whether to build the analysis script now, so it can run on the week-2 data as an early check.
